# Beiyu GLM compatibility branch

This fork preserves the existing two-Spark GLM deployment as the migration
reference: routed experts remain EXL3 K4 MCG, non-expert and vision weights retain
their original precision, and the same BF16 donor `o_proj` tensors must be used.
The upstream base is `47581ccac82660953a5b59cb04b2750d64edc97d`.

The full TP2 package has exported successfully and passed fresh native loads on
both Sparks. Native API acceptance and the text/image baseline comparisons have
passed through native 9999 and NewAPI 8889, including explicit `stop_scope`
forwarding. This does not establish complete vLLM or DFlash2 equivalence.

## Implemented boundaries

- The EXL3 expert-layer gate is complete for the qualified slices below. The
  preparation loader retains the checkpoint's K4 MCG payloads, BF16/F16 scales,
  and TP2 slices. Decode uses the deployed cooperative kernel; prefill reuses
  the original thin/E3 CUDA images extracted from the deployment extension.
  Both are captured kernels, with no serving Python or host routing loop.
  GPU token counts preserve cooperative arithmetic when a large physical graph
  has at most 32 active rows. Invalid and inactive routes cannot alter expert
  counts or write meaningful outputs.
- The GLM CPU image frontend includes resize and padding, fused FP32 CLIP
  normalization, 1176-element temporal patches, two-dimensional vision positions,
  image-token layout and upload packing. Nine reference cases were generated by
  the actual deployment processor with CUDA hidden. They cover tiny images,
  padding, downsampling, the 2048-token budget, narrow images, expanded alignment
  and multiple images. The reference is `tests/frontend/glm53_images.json`.
  The source snapshot defaults to 8000 image tokens, while the reference deployment
  caps each image at 2048. Future GLM exports must explicitly prepare the latter
  budget; do not enable the recipe using the snapshot default.
- Requests can explicitly select `stop_scope: "after_reasoning"` for supported
  text-delimited reasoning parsers. It delays string stops until the initial
  reasoning closes. Omitted/null fields use the listener default; an explicit
  request overrides it. This deployment selects
  `flare run --default-stop-scope after_reasoning`; the upstream default is `all`.
- Checkpoint preflight preserves the F16, I16 and I32 storage types used by EXL3
  and validates their exact byte extents without converting weight payloads.

## Native BF16 text normalization

The BF16 EXL3 preparation uses the same validated original RMSNorm image for
MLA low-rank query/latent normalization and final stream-head normalization.
The shared image owner survives all captured graphs and closes after native
work drains. Text-only EXL3 preparation also requires `--glm-vision-kernels`
with that image directory. Packed NVFP4 preparation retains its historical
FlashInfer `round_before_weight=True` computation; existing packages retain
their captured arithmetic.

Fifteen true-checkpoint norm cases passed original Torch 2.13 CUDA versus
Torch 2.14 compilation, capture and three native replays with zero tolerance:
query width 1536, latent width 512, input/post-attention/final widths 4096,
and rows 1, 17 and 65. Query and latent inputs use the actual stride-2208 fused
projection views. Replay allocated and freed no GPU storage. The reference on
spark-03 is `/output/glm53-text-norm-reference.safetensors`.

```sh
CUDA_VISIBLE_DEVICES=0 python -m qualify.glm_text_norm_reference check \
  --reference /output/glm53-text-norm-reference.safetensors \
  --kernels /runtime/reference-libraries/glm-vision
```

The recorded source calls the actual deployment CUDA norm, rather than a
handwritten approximation. Its reduction differs at a few BF16 rounding
boundaries from a generic FP32 norm, so the qualifier retains exact original
CUDA comparisons. The mHC fused mixing/normalization already multiplies its
FP32 normalized value and norm weight before the BF16 cast; these isolated
norm-vector checks do not qualify the complete mHC operation or text decoder.

## Native two-Spark service entrypoint

Before preparing, build an independent checkpoint with the deployed custom
chat template and exact BF16 donor ranges. `plan` checks every donor's SHA256
and reports the bytes of shards that `create` copies. The output must be new.
Unchanged shards are symlinked, so retain the source mount at the same path until
preparation/export completes. Neither command reads or allocates GPU memory.

```sh
python -m qualify.glm_migration_checkpoint plan \
  --checkpoint /models/ORIGINAL_EXL3_SNAPSHOT \
  --donors /reference/transplant --template /reference/frontend/chat_template.jinja
python -m qualify.glm_migration_checkpoint create \
  --checkpoint /models/ORIGINAL_EXL3_SNAPSHOT \
  --donors /reference/transplant --template /reference/frontend/chat_template.jinja \
  --output /outputs/UNUSED_GLM_TRANSPLANT_CHECKPOINT
```

Prepare/export that directory with the ordinary Flare production exporter,
explicit `--exl3-library /PATH/cooperative_moe.so`,
`--exl3-prefill-library /PATH/exllamav3_ext.so`,
`--glm-vision-kernels /runtime/reference-libraries/glm-vision`, and the validated
TP2/image capacities. The vision directory's `manifest.json`, `rms.cubin` and
`qk.cubin` are preparation inputs; their relative paths and contents enter the
package cache identity. BF16 EXL3 text-only preparation also requires this
directory for exact RMSNorm; the existing text-only NVFP4 path does not read it.
Native serving uses the exported kernels. The EXL3 checkpoint variant already
excludes drafts; omit `--no-mtp`,
which applies only to recipes that declare a learned drafter. Keep checkpoint precision; do not select online activation
or weight conversion to fit memory. Preparation must qualify full target prefill,
decode, cross-host caches, image encode/project/injection and package reload.
The initial ordinary decode path is not DFlash2: the old service uses its external
7-token DFlash2 drafter, while this export excludes learned drafts. Do not claim
speculation or throughput parity from a successful ordinary decode request.

After exporting and verifying the package on both hosts, the entrypoint runs
only the native executable. Select rank 0 on spark-01 and rank 1 on spark-03;
use the actual rank-zero rendezvous address confirmed for those hosts. Start
both processes through the deployment supervisor so they receive SIGTERM.

```sh

  0 10.77.13.1:29901 --publisher-keys /config/publisher.json --verify-weights

  1 10.77.13.1:29901 --publisher-keys /config/publisher.json --verify-weights
```

values can override the latter defaults. The custom template and donors must
